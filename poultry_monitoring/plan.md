- ✅ **Progressive unfreezing** closed most of the gap: stage 2 (fully unfrozen, `lr0=2e-5`) reached val mAP50=0.9874, mAP50-95=0.8919, precision=0.9648, recall=0.9528 — **within noise of ChickenVerse's published `yolo26n`** on both mAP50 (0.9874 vs 0.9872, Δ 0.0002) and mAP50-95 (0.8919 vs 0.8903, Δ 0.0016); not a meaningful "win," the two setups differ enough (freeze schedule, augmentation search) that matching is the interesting result, not beating. Stage-by-stage: stage 0 (freeze=10) 0.9856/0.8802, stage 1 (freeze=5) 0.9875/0.8830, stage 2 (freeze=0) 0.9874/0.8919 — mAP50-95 improved monotonically each stage, mAP50 plateaued after stage 1.
- ✅ `yolo26s` final training (same tuned config, straight `train()`, **no** progressive unfreezing applied) completed: val mAP50=0.9887, mAP50-95=0.9041, precision=0.9670, recall=0.9514 — close on mAP50 (−0.0008 vs ChickenVerse's 0.9895) but a real gap on mAP50-95 (−0.015 vs 0.9191). The size of this gap closely mirrors `yolo26n`'s *pre*-unfreeze gap, suggesting the same unfreeze treatment would likely close most of it — 🔲 **not yet run**, queued as a candidate follow-up (not auto-launched — would compete with the Phase B chain below for the GPU). Should use the directional-contrast augmentation ([ADR 0012](docs/adr/0012-directional-brightness-contrast-augmentation.md)) when it does happen, not the old config.
- ✅ **Fixed for future unfreeze stages**: `DEFAULT_UNFREEZE_STAGES`'s `close_mosaic=10` was inherited unchanged from the tuned config (sized for the original 300-epoch run, ~3% of training). At `epochs=30` per stage it instead disabled mosaic for the last **33%** of each stage (`epoch == epochs - close_mosaic` per Ultralytics' trainer, i.e. epoch 20/30) — visible in stage 2's per-epoch curves as a sharp train-loss drop + a transient val-loss/mAP50-95 dip right at epoch 20, and likely why that stage's early stopping locked in a near-epoch-20 checkpoint. Now follows two rules-of-thumb: **`epochs >> close_mosaic`** (small portion of the stage, not sized for a different run) and **`patience < close_mosaic`** (Ultralytics' `best.pt` always tracks the best-ever-observed fitness regardless of when training stops, so a shorter patience acts as a bounded trial window — if training without mosaic hurts validation, it stops before the rest of the close_mosaic tail is spent on a regime that isn't working). Each stage now uses `close_mosaic=4, patience=3` (was `close_mosaic=10, patience=10`) — not yet re-run against real data, since this was a code fix, not a retrain.
- 🔲 **Benchmark target**: match ChickenVerse's own published `val_mAP50`/`val_mAP50-95` for `yolo26n` (✅ done, within noise) and `yolo26s` (🟡 close on mAP50, gap remains on mAP50-95) — reference table captured 2026-08-11: `yolo26n` val_mAP50/50-95 = 0.9872/0.8903, `yolo26s` = 0.9895/0.9191. **Test split is off-limits for any decision-making** — comparisons and iteration use validation metrics only, to avoid implicitly fitting the test set.
- ✅ **`AutoContrast` cutoff randomized, not tuned**: the augmentation search had converged `autocontrast_cutoff` to a single fixed value (1.2, ~1% of pixels clipped) applied identically every time the transform fired — unlike `RandomBrightnessContrast`'s `brightness_limit`/`contrast_limit`, which Albumentations auto-symmetrizes into a fresh `±range` each call, `AutoContrast.cutoff` has no built-in per-call randomization. Removed `autocontrast_cutoff` from `PARAM_RANGES`/the search entirely; `augmentation/shared.py`'s new `_RandomCutoffAutoContrast` samples a fresh cutoff from a fixed `AUTOCONTRAST_CUTOFF_RANGE = (0.0, 10.0)` every application instead (verified varying across calls). **Compatibility note**: any hardcoded "winning hyperparameters" JSON still carrying an `autocontrast_cutoff` key (e.g. the orchestrator scripts' `HYPERPARAMS` blobs from this session) will now leak that key into `model.train()`'s own kwargs instead of the augmentation builder, since it's no longer in `CUSTOM_AUGMENTATION_PARAM_RANGES` — Ultralytics rejects unrecognized kwargs. Strip that key before reusing any such JSON (e.g. for a future `yolo26s` unfreeze pass).
  - **Follow-up: the range's upper bound is searchable again, without losing per-call variety.** `augmentation/shared.py` cleaned up (less prose, `AUTOCONTRAST_CUTOFF_RANGE` module constant removed) and `_RandomCutoffAutoContrast` now takes `cutoff_max` directly, sampling fresh from `[0, cutoff_max]` every call same as before — but `cutoff_max` is itself a `build_domain_transforms` parameter (`autocontrast_cutoff_max`, back in `PARAM_RANGES`, range `(0.0, 20.0)`). Reconciles the original problem (a single fixed scalar has no sample-to-sample variety) with wanting the search to actually cover this knob: search the *ceiling* of the random range, not the fixed value itself.
- ✅ **`_RandomCutoffAutoContrast` seeding bug, found once the full suite finally ran again**: `get_params()` drew from the bare `random` module instead of `self.py_random` (Albumentations' own per-transform RNG, the one `set_random_seed`/a pipeline's `seed=` argument actually resets) — silently broke `generate_augmented_samples(..., seed=...)`'s reproducibility guarantee. `test_seed_gives_reproducible_draws` caught it immediately once run; hadn't been run since `_RandomCutoffAutoContrast` was added because GPU jobs were live at the time. One-line fix (`self.py_random.uniform(...)`), all 30 tests pass now.
- ✅ **`copy_paste_mode` A/B** (`"flip"` vs `"mixup"`), proxy scale (15 epochs, 30% fraction, `copy_paste` forced to 0.5 since the tuned config has it at 0.0): essentially a wash — `flip` mAP50/50-95/precision/recall = 0.9718/**0.8296**/0.9441/0.9174, `mixup` = **0.9725**/0.8279/**0.9503**/**0.9197**. `mixup` edges ahead on 3 of 4 metrics, `flip` on the harder mAP50-95, but every delta is ≤0.006 on a single unrepeated trial — inconclusive, not a production recommendation either way. The theoretical scale-mismatch risk flagged below (verified from source) didn't show up as a clear mAP50-95 penalty for `mixup` here, which is reassuring but not decisive. Verified from source: `"flip"` pastes a flipped copy of the *same image's own* instances (scale-safe by construction, IoA<0.30 non-overlap); `"mixup"` pastes instances from a *different, randomly-sampled image* at that source image's original scale — no resize/scale-matching step anywhere in Ultralytics' implementation. Real size-matching would need custom compositing (see the cutout-compositing Future Work item below, not a quick fix)
- 🔲 **Flip range worth re-checking deliberately**: the winning tuned config (iteration 1/20, never beaten) has `flipud`≈0 — Ultralytics' stock COCO-oriented default, inherited rather than validated as optimal for this orientation-free overhead dataset. Worth a forced-higher-`flipud` test, not just trusting the tuner's first draw
- ✅ **Augmentation visualization** (`augmentation/visualize.py`): before/after grids for custom Albumentations transforms, with bounding boxes overlaid (`load_yolo_label_boxes` handles both plain-box and segment-polygon label formats). Built-in Ultralytics augmentation is already partly visible via `train_batch*.jpg` (`plots=True`)
- ✅ **Spatial (bbox-aware) custom augmentation** (`augmentation/detection.py`, per `CLAUDE.md` § Package Layout's original "occlusion-aware crops" slot): `CoarseDropout` for occlusion simulation — verified it leaves box coordinates untouched even when a box is fully covered (pixel-level, not geometric), which is exactly what occlusion-robustness training wants. `detection/yolo.py`'s `_build_custom_augmentations` now combines `shared.py` (image-only) + `detection.py` (bbox-aware) into one list; Ultralytics' own wrapper threads bboxes through automatically when any transform needs it
- ✅ **Progressive/gradual unfreezing** (`unfreeze` CLI, `DEFAULT_UNFREEZE_STAGES`): three stages of decreasing freeze + decreasing `lr0` (`10→5→0`, `5e-4→1e-4→2e-5`), each continuing from the previous stage's best checkpoint — result now within noise of ChickenVerse's published `yolo26n` baseline (see line above)
- ✅ **Test-time preprocessing**: compared a deterministic enhancement applied to validation images only (no retraining) via the new `ttp` CLI, against `yolo26n`'s final unfrozen checkpoint. **Clean negative result — none help**: `autocontrast` mAP50-95=0.8912 vs baseline 0.8919 (a wash, ≤0.001 on every metric — the model already saw similar mild autocontrast during training); `clahe` 0.8792 (**−0.0128**) and `hist_eq` 0.8782 (**−0.0138**) both actively hurt, meaningfully so — much stronger, deterministic global transforms than anything trained on, creating a real train/inference distribution mismatch rather than correcting one. Recommendation: no test-time preprocessing in a serving pipeline; baseline is already best. Not pursuing further variants.
- ❌➡️✅ **`multi_scale` training — abandoned run, but the underlying methodology is now fixed**: added `multi_scale: (0.0, 0.3)` to `AUGMENTATION_FOCUSED_SPACE` and ran `model.tune()` for 25 iterations. Stopped at iteration 7 after watching every sampled value land in the `1e-4`–`1e-5` range in the MLflow UI — nowhere near the given range. Root cause traced and documented: [ADR 0005](docs/adr/0005-genetic-tuner-undersearches-from-a-fixed-start.md) — Ultralytics' genetic tuner mutates *multiplicatively* from the current population, and with no real starting diversity (iteration 1 is always pure unmutated defaults), the crossover step's degenerate-span fallback only ever nudges by a tiny amount. **This called the original `AUGMENTATION_FOCUSED_SPACE` tune result into question too** — same mechanism, same small iteration budget, and its winning "iteration 1" was literally unmutated defaults, never beaten across 20 iterations.
  - **Fix implemented and verified**: `tune_hyperparameters` now runs Optuna (`TPESampler`) instead of `model.tune()` — genuinely spans the full given range (Ray Tune considered first, ruled out: no Windows wheels for Python 3.13 in this project's environment). Also **unified with the custom Albumentations search** in the same pass — no ADR 0001 limitation, since the search doesn't route through `model.tune()`'s own subprocess mechanism. Verified end-to-end with a 2-trial/1-epoch smoke test: `flipud`/`copy_paste`/`multi_scale` all sampled genuinely wide, different values per trial instead of clustering near zero, and all 5 custom Albumentations keys came through the unified search correctly.
  - **A second, more serious bug found running this at real scale**: [ADR 0007](docs/adr/0007-subprocess-per-optuna-trial.md) — the first real 40-trial run "completed" (exit 0, printed results) but was silent garbage: trials 3-39 all failed in ~1.3 seconds each with `fitness=0.0`, caught by an overly broad exception handler with no logging. Root cause, found through a multi-step live investigation (not guessed): orphaned DataLoader **worker processes** (Windows `spawn`-based multiprocessing, heavier than Linux `fork`) accumulating across repeated in-process `model.train()` calls, exhausting system RAM — not GPU VRAM (first fix attempt targeted the wrong resource), and not fixable by `del`/`gc.collect()`/`torch.cuda.empty_cache()` since those don't reach child processes. `workers=0` confirmed the mechanism (no leak) but was ~5-6x slower; `workers=4` still leaked, just slower. **Fixed** by running each trial as its own subprocess via the `train` CLI — mirrors exactly what protected the *original* `model.tune()` search from ever hitting this (full process-tree reclaim on exit), while keeping genuine Optuna-driven range coverage and the unified custom-augmentation search. Not yet re-run at real scale with this fix.
  - `run_size_sweep` still runs `tune_hyperparameters` then `tune_augmentation_parameters` sequentially — now partially redundant since the former covers custom params too. Sequential/coordinate search vs. joint search are genuinely different strategies (not strictly one obsoleting the other), so this is a real design decision, not an automatic cleanup — revisit once the unified search has real results to compare against.
  - **Space itself replaced before this fix was ever re-run at scale**: [ADR 0008](docs/adr/0008-conservative-hyperparameter-space.md) — `AUGMENTATION_FOCUSED_SPACE` turned out to be nearly a verbatim copy of Ultralytics' own wide `Tuner.space`, not a considered choice; combined with the "iteration 1 never beaten" evidence above, decided to hand-curate a much narrower, per-parameter space instead (`perspective`, `shear`, `flipud`, `mixup`, `cutmix`, `copy_paste`, `multi_scale` only — everything else fixed at Ultralytics' native default). `lr0` is deliberately excluded too — held fixed for this pass (coordinate search: find the best augmentation config first, tune `lr0` alone in a later pass against that fixed config). `close_mosaic` pulled out of the search entirely, now computed proportionally to each run's own `epochs` via `default_close_mosaic`. **Not yet run at real scale** — this replaces the ADR 0007 fix as the next real GPU-time commitment, not an addition to it.
  - **ADR 0007's subprocess mechanism reverted**: [ADR 0009](docs/adr/0009-revert-to-in-process-optuna-trials.md) — `detection/yolo.py` cleaned up as this project's main script, `tune_hyperparameters` back to calling `train()` directly in-process per trial (no `subprocess`/`sys.executable`/stdout-regex-parsing). Deliberately reopens the RAM-leak risk ADR 0007 fixed, with no mitigation added — a clean, simple objective was prioritized over that robustness, on the record. Worth watching for on the eventual real-scale run.
  - **`yolo.py` split by responsibility**: [ADR 0010](docs/adr/0010-split-yolo-py-by-responsibility.md) — had grown to ~1000 lines mixing single-run train/predict (the actual core) with multi-run search strategies and a test-time-preprocessing harness. Split into `detection/yolo.py` (core train/predict + the still-unified CLI), `detection/tuning.py` (tune/augtune/unfreeze/sweep), `detection/preprocessing_eval.py` (the `ttp` comparison harness, now also home to a domain-informed `brightness_contrast` candidate — crush the dark background, mild contrast gain, since ChickenVerse birds are white against dark litter). `prepare_data` moved into `data/coco.py`. `python -m poultry_monitoring.detection.yolo <subcommand>` unchanged; `yolo.py`'s `main()` imports the other two modules locally (not at module top level) to avoid a circular import, since both of them import core pieces (`train`, `SEED`, `CLASS_NAMES`) from `yolo.py`.
  - ❌ **Real-scale result, finally in — negative**: [ADR 0011](docs/adr/0011-conservative-search-result-not-adopted.md) — the 16-trial search's winner (`box_map50_95=0.8166` on the search proxy) underperforms the pre-session baseline at real scale in *both* regimes tested. Warm-start (`progressive_unfreeze_train`, schedule matched exactly to baseline): `0.8750` vs. `0.8919` (**Δ −0.0169**). Cold-start (`train()` from stock `yolo26n.pt`, the exact regime the search itself uses, config matched except a since-fixed `close_mosaic` difference that should help not hurt): `0.8482` vs. `0.8768` (**Δ −0.0286**, the larger regression). The cold-start curve converges completely normally (`0.70→0.84` over ~45 epochs, clean patience-stop) — not the destabilization seen in the warm-start runs, just a genuinely worse optimum. **Not adopted anywhere.** Production baseline reverts to the pre-session near-Ultralytics-default augmentation config. Doesn't invalidate ADR 0008's space-design rationale — only this specific 16-trial run's winner is ruled out, not the narrower-space approach itself.
  - ✅ **Directional brightness/contrast — new best, adopted**: [ADR 0012](docs/adr/0012-directional-brightness-contrast-augmentation.md) — took the same "birds are white, background is dark litter" observation that failed twice (test-time preprocessing above, and via the ADR 0011 search) and applied it as an *asymmetric, training-time* `RandomBrightnessContrast` bias (`brightness_limit=[-0.35,-0.05]`, `contrast_limit=[0.3,0.7]` — always darken, always boost contrast, but still randomized per-call, not a fixed value) instead. Zero code changes needed — Albumentations already accepts asymmetric tuples, and this project's hyperparameter plumbing already passes values through untouched. Cold-start: a wash (`+0.0001`). Full progressive-unfreeze chain: behind at stages 0-1, then **beats the all-time-best final number** at stage 2 — `box_map50_95=0.8929` vs. `0.8919` (**Δ +0.0010**), `box_precision` up `+0.0058`, `box_recall` down `-0.0040`. Modest, but real, and the first configuration all session to actually beat the pre-session baseline end-to-end. **Adopted as the new production `yolo26n` config** — `yolo26n-unfreeze-directional-contrast-stage2` is the new best checkpoint. `augmentation/shared.py`'s own function defaults deliberately left unchanged (this is a specific override, not a new default — see ADR 0012 Consequences).
- ⏭️ DETR detection baseline (Hugging Face `transformers`) — secondary/practice track, pursued when there's time; not required before calling YOLO26 detection "done," and not a blocker for Phase 3

## Phase 3 — Segmentation Baseline (in progress)

Deliberately **simpler than Phase 2's detection track** — no hyperparameter search, no custom photometric/geometric augmentation pipeline. This phase exists to answer one specific question cleanly: **does the synthetic copy-paste pipeline help, isolated as the only variable?** Model sizes, epochs, and base augmentation all stay at Ultralytics' stock defaults throughout both stages below — mirroring ChickenVerse's own training methodology (fixed config, no search, see Phase 2 § Training Configuration) rather than this project's own tuned/searched detection recipe. Tuning/searching segmentation the way Phase 2 did detection is explicitly not the plan here; if that ever changes, it's a new phase, not a silent scope-creep into this one.

Starting point: `notebooks/03_explore_segmentation.ipynb` — mask quality checks, COCO→YOLO-seg conversion fidelity (found and fixed a real bug, [ADR 0013](docs/adr/0013-rle-to-polygon-preprocessing-for-yolo-seg-conversion.md)), and the synthetic copy-paste prototype ([ADR 0014](docs/adr/0014-copy-paste-donor-bank-design.md)/[0015](docs/adr/0015-color-aware-donor-compositing.md), promoted here from Future Work — see that section for the design history).

- ⏭️ **RGB-D 4th input channel — depth-assisted instance separation** — intuition: in a dense overhead scene, a depth channel should make touching/overlapping bird boundaries easier to separate than color alone, since occlusion is fundamentally a depth-ordering problem, not a color one. This is an architecture-modification track parallel to Phases 2/3, YOLO26 only for now (see scope note below), tracked separately because it changes the model's input contract, not just the data pipeline.
  1. **Depth source is already in-house — don't add a new dependency.** The installed `ultralytics` (8.4.117 at time of writing) ships a native `depth` task: `ultralytics/cfg/models/26/yolo26-depth.yaml` (YOLO26 backbone + FPN + DPT-style dense decoder head, "follows the Depth Anything approach") with downloadable checkpoints `yolo26{n,s,m,l,x}-depth.pt`. Usage: `YOLO("yolo26n-depth.pt").predict(img)` → `results[0].depth` is a dense per-pixel map already rescaled to the original image size (see `ultralytics/models/yolo/depth/predict.py`). Same framework/license as the rest of the project (constitution Principle I) — this is very likely what "yolodepth" was half-remembering. **Nuance to remember**: its output is explicitly documented as *unbounded log-depth*, not a 0–255-style map — it will need an explicit normalization step before it can be treated like a "color" channel (see point 5).
  2. **Fusion architecture: early fusion (single 4-channel tensor), not a two-input graph.** A two-stream design (one input still using Ultralytics' built-in image augmentation, a separate depth input) sounds cleaner but means forking `BaseTrainer`/`BaseDataset`/the `model.train()`/`.predict()` convenience API to carry a second tensor through — large, ongoing-maintenance surgery. Checked directly against `ultralytics/data/augment.py`: most geometric transforms are already channel-count agnostic and don't need this workaround —
     - `Mosaic`: canvas is `np.full((s*2, s*2, labels["img"].shape[2]), 114, ...)` — reads channel count dynamically.
     - `LetterBox`: `np.full((h,w,c), fill_value=self.padding_value, ...)` — same, scalar broadcasts.
     - `RandomPerspective` (`cv2.warpAffine`/`warpPerspective`): `borderValue=(114,114,114,114)` — already a 4-tuple, applies cleanly to a 4-channel array without erroring (though semantically padding a depth channel with a fixed 114 "fake distance" is questionable — worth overriding to a depth-specific sentinel, e.g. 0, once this is built).
     Only the **photometric-only** transforms need patching to leave channel 4 alone: `RandomHSV.apply_image` currently has a blunt guard (`if img.shape[-1] != 3: return labels`) that will silently skip *all* HSV jitter — including on the RGB part — once the array is 4-channel; needs to instead slice `img[..., :3]`, augment, and reattach channel 4 untouched. Same slice-and-reattach treatment needed for the `Albumentations` wrapper (blur/CLAHE/ToGray etc. all assume 3-channel). **Net effect: patch two functions, keep everything else — `model.train()`/`.val()`/`.predict()` stay usable unmodified.**
  3. **Model surgery**: `DetectionModel`/`SegmentationModel.__init__(cfg, ch=3, ...)` already accepts `ch=4` against the stock `yolo26n(.yaml|-seg.yaml)`. To keep the pretrained-COCO warm start (rather than training the stem from scratch): load the pretrained 3-channel state dict, then for the first conv's weight `[out_ch, 3, kH, kW]` build `[out_ch, 4, kH, kW]` by copying slices 0–2 verbatim and setting slice 3 = `weight[:, :3].mean(dim=1, keepdim=True)` — mean-of-RGB init for the new channel, so a "typical" depth map produces roughly the activation the pretrained net already expects, giving fine-tuning a stable starting point instead of noise. Standard trick for channel-inflated pretrained nets (RGBD/NIR+RGB literature); belongs as a small function (e.g. `load_rgbd_weights(model, weights_path)`) in `detection/yolo.py` alongside the wrapper.
  4. **Precompute + cache depth offline — don't run the depth model live inside the training loop.** Depth must be computed once per source image and stay pixel-aligned through whatever geometric augmentation runs afterward (mosaic/perspective/flip act on the whole 4-channel array together, per point 2 — this is exactly why early fusion keeps augmentation simple). Plan: an offline script over train/val/test producing one depth map per image (`data/depth_cache/<split>/<image_id>.png`, normalized to 8-bit — see point 5), then a `YOLODataset` subclass that concatenates image+depth in `load_image()`, before augmentation runs. Fits as a `data/depth.py` addition to the package layout (precompute + normalize + cache), separate from the GPU-loader work in `data/dali_pipeline.py` (Phase 5).
  5. **Normalization**: Ultralytics doesn't mean/std-normalize RGB, just `/255` — so the log-depth output needs an explicit mapping into the same uint8 "color channel" convention *before* caching (e.g. percentile clip + min-max → `[0,255]`). Open question: per-image normalization (robust, but discards absolute-scale cues) vs. per-facility normalization (these are fixed overhead rigs, so a per-facility fixed range would preserve relative depth/scale across images from the same camera) — try per-facility first, fall back to per-image if it's too brittle across facilities.
  - **Testing/validation ladder — cheapest checks first, gate spending effort on each passing**:
    1. **Qualitative check, zero code changes**: in a Colab exploration notebook (per constitution Principle II), run `yolo26n-depth.pt` on a handful of ChickenDet images, overlay the depth map against GT instance masks, and specifically eyeball *touching/overlapping* birds. Open question this is actually testing: overhead-rig birds are ~15–20cm tall shot from several meters up — does monocular relative depth resolve bird-to-bird boundaries at that scale, or does it just recover the (uninteresting) camera-to-floor gradient? If depth boundaries don't track the occlusion boundaries that matter, stop here.
    2. **Cheap ablation, no architecture surgery**: swap depth in for one existing RGB channel (e.g. blue) instead of adding a 4th, using the stock pretrained 3-channel checkpoint completely unmodified. Fine-tune on a subset, compare mAP delta vs. the RGB baseline. Fast signal on whether depth carries separating signal at all, before investing in channel-inflation + augmentation patches.
    3. **Full 4-channel path** (points 2–5 above) only once 1–2 look promising. Log as a run with new params (`input_channels`, `depth_source`) in the *same* `poultry_detection`/`poultry_segmentation` MLflow experiments as the RGB baseline, so it's directly comparable (constitution Principle IV).
    4. **Control experiment**: also run a variant with the 4th channel filled with noise (same weight-init trick, same architecture). Isolates whether any mAP gain is really from depth signal vs. just the extra parameters/regularization effect of a wider first conv — needed before claiming "depth helps" in the write-up.
  - **Downstream implications to remember**: if this pans out, Phase 6 export/benchmark numbers become a **two-model pipeline** (depth net + detector) at inference time, not just the modified detector's forward pass — must be disclosed under constitution Principle V, not silently compared against the single-model RGB baseline's latency. Also **DETR is out of scope as described** — its patch-embedding/stem would need separate, differently-shaped channel-inflation surgery; don't assume this generalizes to the DETR side of the head-to-head without redoing this analysis there.
  - **Why it's worth doing**: cheap to validate (step 1 of the testing ladder is a notebook cell, not an engineering project) before committing to the model-surgery work, and — unlike the synthetic-data idea above — reuses a model already inside the project's own dependency tree rather than introducing a new one.
